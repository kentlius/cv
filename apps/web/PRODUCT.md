## Platform

web

## Users

**Primary (confirmed): engineers and peers.** Readers are technical people who
arrive from LinkedIn and GitHub profile links or from engineering communities,
and they judge the work the way engineers do: what was built, at what scale,
under what constraints, and how cleanly it is put together.

The same person is also the subject of a formal PDF CV; that document is
generated by the same repository, but the website is the artifact aimed at the
engineering audience above. All paths in this record are repo-root relative.

## Product Purpose

One personal CV for Kent Liusudarso, a software engineer in Shizuoka, Japan.
The same structured source produces a browsable website and a rendered PDF, so
the facts a reader sees in either place cannot drift apart.

Beyond presenting the CV, the website's job is to **demonstrate engineering
craft** — the site's implementation, interaction, and output quality are part
of the argument being made to its readers (confirmed).

## Positioning

A neighboring CV site could copy the layout; it could not truthfully claim the
mechanism behind this one. A single YAML source (`cv/source/cv.yaml`) is
expanded into locale-specific RenderCV documents, rendered to PDF release
assets, and imported directly by the web build through a content collection.
Parity between the web page and the PDFs is enforced in CI, and the site is a
small enough Astro application that a technical reader can inspect how it is
built.

## Operating Context

- The CV is edited only in `cv/source/cv.yaml`. `pnpm cv:build` expands it to
  `cv/Kent_Liusudarso_CV.yaml` (English) and `cv/Kent_Liusudarso_CV_ja.yaml`
  (Japanese); both generated files are committed and never hand-edited.
- The web build imports the generated English YAML by path at build time; there
  is no runtime fetch and no CMS.
- CI runs the web tests, builds the site, verifies the generated YAML matches
  the source, and smoke-renders the CVs.
- Pushing a `v*` tag renders every CV and replaces the PDFs attached to the
  GitHub release.
- The site deploys to Cloudflare Workers static assets at
  `https://cv.kntl.zip`.
- Japanese exists as a PDF locale; the website renders the English document
  only.
- Analytics is provided by Cloudflare Web Analytics at the zone level, injected
  by Cloudflare rather than loaded by a page script. It reports aggregate
  visitors, page views, paths, referrers, countries, devices, and browsers; it
  does not identify individual people.

## Capabilities and Constraints

Confirmed and observed:

- A single page presents the profile header and contacts, experience,
  education, certifications, awards, and skills; a styled 404 handles missing
  paths.
- Contact channels are email, phone, LinkedIn (`kentlius`), and GitHub
  (`kentlius`).
- A small monochrome globe in the footer marks the location. Cobe is loaded
  only as the footer approaches; a static SVG wireframe is the fallback, and
  reduced motion keeps the wireframe instead of starting WebGL.
- The Open Graph image is generated at build time from the same CV data with
  Satori and Resvg (`/og.png`, 1200×630). There is no hand-made social image.
- Initial and scroll reveals are progressive enhancement: content is visible
  without JavaScript, disabled under `prefers-reduced-motion: reduce`, and
  forced visible for print. The reveal script, footer globe script, and
  confetti/console script are the only authored client-side scripts; the rest
  of the page is static HTML. Cloudflare Web Analytics is injected at the zone,
  not by a page script.
- Print styles disable all reveal motion and hide the footer globe to keep the
  CV as a document.
- Content is derived from the generated YAML; the web app holds no authored CV
  copy of its own.
- There is no headshot asset; the avatar is rendered from initials.
- No server, database, or runtime content source exists in the web app.

Undecided (asked during init, left unanswered — do not treat as commitments):

- Which current implementation properties are binding product constraints:
  English-only web page, static-first with minimal client JS, print/PDF parity,
  and a specific accessibility standard (e.g. WCAG 2.2 AA) were all left
  unset. They describe today's behavior, not a confirmed requirement.

## Product Principles

1. **The craft is the claim.** For an engineering audience, the pipeline, the
   interaction quality, and the code are part of what is being evaluated, not
   decoration around a résumé.
2. **One source, no drift.** Every fact the site displays derives from
   `cv/source/cv.yaml`; derived files are generated, never hand-maintained, and
   parity is verified in CI.
3. **Facts only.** No invented metrics, testimonials, logos, or capabilities.
   If it is not in the source or backed by a real link, it does not ship.
4. **Content first, interaction second.** The CV is readable and printable
   before any script runs; JavaScript adds speed and delight, never access.
5. **Stay small enough to audit.** A static build, two authored client scripts,
   and no runtime content source keep the whole surface comprehensible to the
   readers it is meant to impress.
